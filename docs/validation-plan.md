版本：v0.2（审查修订设计稿）· 2026-11-02 · 配套：[架构](technical-design.md)、[数据与状态](data-and-state-contracts.md)、[实施](implementation-plan.md)、[review](review-report.md)

**状态声明**：这里的产品运行、媒体与故障注入验收均尚未执行。文档审查中的 SQL/JSON 静态与内存约束检查见 `review-report.md`，不能代替产品验收。本文定义通过条件，不声称系统已满足。

## 1. 验收分层

| 层 | 目的 | 何时跑 | 失败处理 |
| --- | --- | --- | --- |
| L0 单元 | 状态机、守卫、纯函数 | 每次改动 | 阻断合并 |
| L1 集成 | coordinator + SQLite + gateway + 对象库 | 每工单完成 | 阻断里程碑 |
| L2 故障注入 | 断电/失联/外部超时 | 每里程碑 + 发布前 | 阻断里程碑 |

| L4 人工校准 | 质检标准与真实观感对齐 | 首批 10 条 | 调整标准 |

## 4. 故障注入（L2）

前置：可复现脚本 + 观测点（DB 查询 + 事件流 + 网络/进程钩子）。每个用例记录**预期状态**与**禁止状态**。

### 4.1 桌面与租约

| ID | 注入 | 步骤 | 预期 | 禁止 |
| --- | --- | --- | --- | --- |
| F1 | 执行者被杀 | 持租约时 `kill -9` 进程组 | revoking先封禁/增epoch→排空动作→取得终止证据→封存录制→新租约 | 仅因 TTL 到期就分配 |
| F2 | 执行者被挂起 | `SIGSTOP`，并保留已排队CDP/输入请求 | 超时只触发撤销；必须有终止与在途动作清理证据，旧epoch拒绝；否则隔离 | 以探活超时作为死亡证明，或旧队列在新租约下继续执行 |
| F3 | 网关崩溃 | kill gateway | 所有租约标 revoking；重启 epoch 从磁盘续增 | epoch 回退到 1 |
| F4 | DB 从旧备份恢复 | 恢复 epoch 较旧的 DB | 网关拒绝低 epoch；job `needs_input` | 旧执行者"复活"成功 |
| F5 | 无法确认失活 | 终止回执缺失/动作结果未知 | 资源 `quarantined`，不分配；无法隔离时只可转单独验收的人工监督流程 | 仅记告警就继续无人值守 |
| F6 | 录制中 OBS 断开 | 停 OBS | 已写文件被捕获、校验；`gaps` 记录 | 静默重录并覆盖 |
| F7 | 陈旧截图误判 | 页面显示"成功"但结果文件无效 | `test_runs.result='failure'`，证据标不符 | 以提示文案作为成功证据 |

### 4.2 外部提交

| ID | 注入 | 步骤 | 预期 | 禁止 |
| --- | --- | --- | --- | --- |
| F8 | 提交超时但外部已成功 | 代理丢弃响应 | op=`UNKNOWN`；对账查到已存在→`RECONCILED`；意图进 `accepted` | 重发请求 |
| F9 | 提交成功但 DB 未落盘 | 在事务C 前 kill avcd | 重启后 journal 存在 `SUBMITTING` → `UNKNOWN` → 对账 | 直接判失败并重试 |
| F10 | 否定对账 | 先返回普通404，再提供覆盖账号/请求及可见性窗口的权威未受理证明 | 404保持UNKNOWN；权威证据+新的人类批准才允许一个后继操作，新op/key关联旧op | 将列表暂缺当作没提交、无限后继链 |
| F11 | 对账查询持续失败 | provider 全 5xx | 保持 UNKNOWN，退避 ≤6 次/24h，之后 `needs_input` | 超限后自动重提 |
| F12 | 人工上传未回填 | 人已发作品，不回填 | 状态保持 `unknown`，不得由系统再发 | 系统自动补发 |
| F13 | 重复审批/发送 | 同意图两次approve、发送者双重CAS、崩溃后重放send_claim | 同键幂等读回；发送许可只被领取一次，恢复只对账 | 重复外发或自动重放磁盘ticket |

## 5. 媒体全片质检（L3/L4）

### 5.1 必须全片，不可抽帧替代

`[决定]` 质检分两条独立证据流，缺一不可：

1. **确定性全解码**：`ffprobe` 全文件 + 逐帧解码（不丢帧），统计：
   - 容器/编码/时长（58–62s）/分辨率（1080×1920）/帧率（30±0.1）/像素格式；
   - 音轨存在、采样率、声道、整体响度（LUFS）与真峰值；
   - 黑帧序列（`blackdetect`）、冻结帧（`freezedetect`）、静音段（`silencedetect`）的区间列表。
2. **视听覆盖审看**：审看者（人或 Agent）必须按**连续区间**记录审看日志（`coverage.jsonl`），每段含 `t_start,t_end,verdict,notes`；时间区间先求并集并裁剪到 `[0,duration]`，不能按相加时长掩盖重叠；视频每帧、音频全时段均被审看，才允许 `pass`。边界浮点误差只允许一帧/一采样级规范化，不能允许一段未审看内容。日志必须绑定MP4哈希、审看者身份、开始/完成时间与问题记录；日志本身不是已看听的证明，首批需人工完成。

> 抽帧拼图、字幕转写、制作方自述**都不是**任何一项的替代。它们最多作为审看的辅助索引。

### 5.2 检查项与判定

| 类别 | 检查 | 通过条件 | 证据 |
| --- | --- | --- | --- |
| 技术 | 全解码无错误 | 0 error | 解码日志 |
| 技术 | 时长/分辨率/帧率 | 在容差内 | ffprobe JSON |
| 技术 | 音轨与响度 | 有音轨，LUFS 在目标窗（如 -16±2，`[假设]`） | 响度报告 |
| 技术 | 黑/冻/静音 | 非预期段 = 0；预期段在 `edit_plan` 中登记 | 检测区间 vs 计划 |
| 内容 | 镜头与旁白一致 | 逐段核对，无错配 | 审看日志 |
| 内容 | 字幕 | 与音轨逐句一致，无错别字、无溢出安全区 | 字幕 diff + 帧检查 |
| 内容 | 事实断言 | 每条 claim 有证据，且画面/文案与 test_run 结果一致 | claim→evidence 查询 |
| 内容 | 对比一致性 | 前后对比的裁切/缩放/时长一致 | 参数核对 |
| 内容 | 素材使用 | 全部通过当前用途的许可门禁（cleared/public_domain/first_party_owned，且满足适用条件），标注符合要求 | 许可清单 |
| 观感 | 可读性/节奏 | 人工评分 ≥ 阈值 | 评分表 |

### 5.3 人工校准（L4）

- 首批 10 条：每条至少由**一名人类完整看听**，另一个独立审查者复核；有两位人类时独立比较，不把人力配置假设当作已具备条件，比较各自 verdict 与问题定位。
- 计算一致性：若对同一缺陷的定位一致率 < 80%，修订检查单（不是放宽标准）。
- 校准产物：`qa_calibration.md` 记录分歧点、最终判定依据，作为后续自动判定的参照。
- `[待验]` 模型审看的可靠性：在 10 条中**人为植入 3 个缺陷**（错字、静音段、镜头与旁白错配），要求在覆盖日志中被定位；未全中则提高人工比例。

### 5.4 渲染与录屏性能

| 项 | 方法 | 通过条件 |
| --- | --- | --- |
| 渲染与桌面并行的影响 | 同时录屏与渲染，比较帧率/丢帧 | 帧率下降 < 10% 且无丢帧；否则降为串行 |
| 录屏本身开销 | 同操作开/关录屏对比 | 关键操作耗时差异 < 15% |
| 渲染时长 | 单条 60s 成片 | 记录实测值，作为成本输入（不给承诺值） |

## 6. 实测真实性（L3）

| 检查 | 方法 | 通过条件 |
| --- | --- | --- |
| 操作真实发生 | 录屏逐帧可见点击/输入 | 与 `capture_manifest` 时间点对齐 |
| 结果真实存在 | 打开结果文件/链接 | 内容与录屏末段一致 |
| 输入可复现 | 按记录重放输入 | 得到同类结果（允许非确定性工具，需注明） |

| 非"演示视频"冒充 | 来源核对 | 所有"实测"镜头均来自本 job 的 capture |

## 7. 内容许可、账号权限与发布对账（L3）

### 7.1 许可

- 渲染前：程序硬门禁（doc2）。
- 发布前：人工核对发布包中的"素材来源与许可清单"，逐条与 `asset_licenses` 一致。
- 抽查：随机 20% 素材回溯到条款快照，确认 `terms_text` 与快照一致。
- 失败即阻断发布，不"先发后补"。

### 7.2 账号与权限

| 检查 | 通过条件 |
| --- | --- |
| 账号是目标账号（非测试号） | 账号名与 job 配置一致，且有当次登录态证据 |
| 权限存在 | 人工在平台侧确认可发布；记录核查时间 |
| 凭证不落仓库 | 全仓扫描无凭证；日志抽样无明文 |
| 代发告知 | 发布行为由人类执行或明确知情（平台要求） |

`[已知]` 抖音要求每次代用户发布让用户明确感知；首版由人执行，天然满足。若将来自动化，需重新评估。

### 7.3 发布对账

| ID | 场景 | 通过条件 |
| --- | --- | --- |
| E4-a | 正常发布 | 回填 `work_id/url/published_at`，`final_state='public'`，可按 URL 打开 |
| E4-b | 提交后超时 | 无重复作品；最终状态由对账确认 |
| E4-c | 已上传未回填 | 系统不自动重发，进入人工对账 |
| E4-d | 审核中 | 状态 `reviewing`，不得记 `published` |
| E4-e | 被拒 | `rejected` + 原因，保留成片版本，不自动改文案重发 |
| E4-f | 修改后重发 | 新 `video_version` + 新 intent（新 dedupe_key），旧作品记录保留 |

**验收结论用语约束**：只有 E4-a 通过且 `publications.verified_by` 为人类时，才可写"该账号该次发布已核实"。不得写"自动发布已可用"。

## 8. 预算上限测试

| ID | 场景 | 预期 |
| --- | --- | --- |
| B1 | 估算使总额超限 | `budget_blocked`，未产生 attempt，无外部调用 |
| B2 | 运行中追加有费操作 | 每操作重新预留，余额不足不发送；不能靠stage初始估算无限调用 |
| B3 | hard与soft边界 | hard拒绝无可执行上界操作；soft实际高于估算按实入账并告警/阻断新调用；不得宣称无超支 |
| B4 | 取消后结算 | 证明未发送才释放；可能发送保留unknown预留；已结算不重复变化 |
| B5 | UNKNOWN 期间 | 预留**不释放**，直到对账完成（防乐观超额） |
| B6 | 重复结算 | 相同settlement_key读回原结果，不同key修改终态拒绝；其他reservation余额不能掩盖重复释放 |
| B7 | 人工调高上限 | 独立管理身份认证；Agent伪造PTY失败；记录approved_by和前后额度 |

## 10. 退出标准（"这个系统可以用了"）

全部满足才可对外描述为"首版可用"：

1. L0/L1 全绿，L2 全部故障用例通过。
2. 至少 1 条真实样片走完 M2–M5，且 E4-a 由人类核实。
3. 从SQLite一致性备份＋对象引用闭包＋模板/渲染器版本＋必要journal，在独立临时目录恢复任务与发布事实。只保留媒体objects的缺失备份必须阻断发布恢复，不能推断未发布后重传。
